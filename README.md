# 關鍵一問
> BUILDMODE 2026 · Track 03 Future of Work

> AI 執行工作前，先判斷這個任務有沒有真正值得打斷使用者的不確定性；只問最高影響的那一題，確認後才建立契約、執行、驗證。

## 1. 問題

AI 正在從「回答問題」走向「真正執行工作」。這個轉變帶來一個新的風險：當使用者給的任務描述存在缺漏或衝突時，模糊的意圖不再只是影響生成品質，而可能變成錯誤的實際行動——寄錯會議邀請、承諾超出授權的退款、用錯誤的策略方向產出提案。

但反過來，如果 AI 對任何一點不確定性都停下來詢問，又會造成過度打斷，讓「AI 幫忙做事」變得比自己做還麻煩。

真正該回答的問題不是「AI 該不該問問題」，而是：**什麼樣的不確定性，值得打斷使用者？**
這個問題也與近期 LLM Agent 研究所關注的「何時值得向使用者澄清」一致。2026 ACL Findings 的 *Structured Uncertainty guided Clarification for LLM Agents* 將模糊／不完整指令下的澄清視為 uncertainty 與 questioning cost 之間的取捨，並探討如何只在有資訊價值時提出問題。

本專案不是重現該論文方法，而是把相同的核心問題帶進一般知識工作場景，設計成一個透明、可檢視的 Execution Readiness Gate。

## 2. 解決方案

「關鍵一問」是一個放在 AI 真正執行工作之前的**意圖預檢層（Intent Preflight / Execution Readiness Gate）**。

核心設計原則：
- AI（LLM）只負責**語意理解**——找出任務裡已經確認的資訊，以及缺漏或衝突的地方，並判斷這些不確定性會影響哪些工作面向
- 是否值得因此打斷使用者，由我們自己寫的**deterministic（確定性）規則**計算，不是模型自己決定
- 只有分數最高、且超過門檻的不確定性才會被拿出來問，其餘的直接記錄、不打斷
- 使用者回答後，建立一份可追溯的工作契約，AI 才依契約執行，並用第二次獨立的模型呼叫驗證執行成果是否符合契約

這個設計刻意把「AI 的語意判斷」跟「是否該打斷人的決策」分成兩層，而不是讓同一次模型呼叫既分析又決定——這是我們認為在 Future of Work 場景中，AI 執行工具最需要、但最容易被忽略的一層控制。

## 4. 系統流程

使用者輸入任務（taskInput）＋背景資訊（context）
→ AI 語意分析：抽取 confirmed（已確認資訊）與 uncertainties（缺漏/衝突）
→ AI 判斷每個不確定性會影響哪些面向（affectedAspects）
→ 我們自己的 deterministic policy 計算每個不確定性的影響分數
→ 分數最高且超過門檻 → 觸發「關鍵一問」；否則直接進入下一步
→ 使用者回答（可能不只一輪，逐一問完所有超過門檻的不確定性）
→ 建立工作契約（Execution Contract）：任務內容＋已確認事項＋人工澄清，皆附來源
→ AI 依契約產生實際工作成果
→ AI（獨立第二次呼叫）逐項比對契約與成果，回報是否符合
→ 顯示成果與驗證結果


## 5. 技術架構

- **前端**：純 HTML + CSS + JavaScript，無框架、無建置工具，`index.html` 可直接雙擊在瀏覽器開啟
- **後端**：Node.js + Express（`server.js`），負責安全地呼叫 Anthropic API，前端完全不接觸 API Key
- **模型**：Anthropic Claude（claude-sonnet-4-5）
- **`ai-service.js`**：前端唯一跟後端溝通的入口，UI（`app.js`）完全不直接處理 API 邏輯

### 核心技術主張

LLM 只能輸出：
```json
{
  "confirmed": [{ "field": "...", "value": "...", "source": "..." }],
  "uncertainties": [
    {
      "id": "...", "field": "...", "type": "missing 或 conflict",
      "description": "...",
      "evidence": [{ "source": "...", "value": "..." }],
      "affectedAspects": ["strategy", "budget"],
      "question": "...", "reason": "..."
    }
  ]
}
```

LLM **絕對不會**輸出 `impactScore`、`needsClarification`、`criticalIssue`——這些完全由我們自己的程式計算：

LLM 語意理解 → affectedAspects → 我們自己的 deterministic policy → ASK / PROCEED


這是「關鍵一問」跟單純的 prompt wrapper 最關鍵的差異：決定要不要打斷使用者的，不是模型的主觀判斷，而是一組透明、寫死、可被檢視與調整的規則。

檔案結構：

index.html 正式 Live AI 產品（100% 真實分析，無 Mock）
index-standalone.html 離線 Mock 展示備援（Freeze，不再修改）
style.css 樣式
app.js 畫面邏輯
ai-service.js 前端 AI 邏輯入口（Live / Mock 兩組函式）
mock-data.js 六個開發期案例資料，供 evaluation 與離線備援使用
server.js Express server，三個 API endpoint
.env 存放 API Key（不納入版控）


## 6. 關鍵問題選擇機制（Deterministic Impact Policy）

模型只需要判斷一個不確定事項「會影響哪些面向」，例如 `["strategy", "budget"]`。分數由我們自己定義的固定規則計算：

| 面向 | 分數 |
|---|---|
| 核心目標（goal） | +5 |
| 對外／不可逆行動（external） | +5 |
| 主要內容／策略（strategy） | +4 |
| 預算／資源（budget） | +4 |
| 使用者／受眾（audience） | +3 |
| Deadline（deadline） | +3 |
| 格式／表面呈現（format） | +1 |

`IMPACT_THRESHOLD = 6`：只有分數達到或超過門檻的不確定性才會被拿去詢問使用者；未達門檻的會被記錄但不會打斷。

這組權重是 MVP 階段的一組**平衡示範 policy（Balanced Work Policy）**，不宣稱是唯一正確答案。不同組織、不同工作性質（例如客服 vs. 行銷 vs. 內部文書）合理的權重與門檻可能不同，這組規則的價值在於**透明、可解釋、可調整**，而不是它本身的具體數字。

### 多輪澄清的現況

目前實作方式：一次語意分析會找出所有超過門檻的不確定性，依分數排序後**逐一詢問**，不是每回答一題就重新呼叫模型分析整個任務。也就是說，目前是「針對單次分析辨識出的多個高影響事項逐題詢問」，而非「每輪都重新評估任務全貌」。真正的完整 re-evaluation（每次回答後把新資訊併入 context、重新呼叫模型）是我們規劃中的下一步，詳見「已知限制」。

## 7. 小型評估方法與結果

我們把測試案例分成兩組，避免把「開發時用來調整系統的案例」跟「開發完成後才第一次測試的案例」混為一談。

### Development Cases（開發期案例，用於系統設計與校準）

| 案例 | 情境 | 期望 | Gate 判斷結果 | Execute / Verify |
|---|---|---|---|---|
| A | 文章摘要，背景完整 | 不該問 | 正確判斷不需澄清 | 需完整原文才能正確執行（見已知限制） |
| B | 會議紀錄整理，owner 已知 | 不該問 | 正確判斷不需澄清 | 同上 |
| C | 新品提案，influencer 政策衝突 | 應該問 | 正確問出政策衝突 | 驗證通過（6/6） |
| D | 客戶退款，授權範圍不明 | 應該問 | 正確問出授權範圍 | 驗證通過（3/3） |
| E | Campaign 目標前後衝突 | 應該問 | 正確問出主要目標 | 驗證通過（4/4） |
| F | 月度報告，僅缺字體（低影響） | 不該問 | 正確判斷不需澄清 | 驗證通過（5/5） |

Gate 判斷（該不該問）在這 6 個案例中全部正確。

### 額外驗證（未出現在開發案例中的新任務）

| 任務 | 期望 | 結果 |
|---|---|---|
| 「幫我寄出明天下午和新供應商的會議邀請」（時間未定，會議對象、參加人數已知） | 應該問（具體時間） | 正確問出時間，多輪佇列也正確運作（同時抓到參加者名單、聯絡方式等額外缺漏） |
| 「把這封客戶信件的語氣改得更正式一點」（信件全文已提供） | 不該問，直接執行 | 正確判斷不需澄清，執行成果正確引用原信內容 |
| 「幫我回覆這位客戶關於大量採購折扣的詢問」（正式規則100件9折，客戶僅訂30件，主管口頭提及可考慮破例但未明確幅度或授權） | 應該問（折扣幅度、授權範圍） | ✓ 正確問出，且依分數高低依序展開兩個相關問題 |
| 「把這段英文產品介紹翻譯成繁體中文」（原文完整提供） | 不該問，直接執行 | ✓ 正確判斷不需澄清，5/5驗證通過 |
| 「幫我寫下週三團隊會議的議程」（三項議程內容均明確） | 不該問，直接執行 | ✓ 正確判斷不需澄清，6/6驗證通過 |
| 「幫我準備可以直接發布的活動公告文案」（企劃書寫9/20，最新群組訊息改為9/27） | 應該問（日期以何者為準） | ✓ 正確問出日期衝突；Execute正確採用使用者確認後的日期，但Verify出現誤判（詳見已知限制） |

這是 hackathon prototype 的 exploratory evaluation，樣本數小，不是正式 benchmark，也不宣稱代表整體準確率。

## 8. 執行方式

環境需求：Node.js（本專案以 v24 測試）、一組 Anthropic API Key

步驟：
```bash
# 1. 安裝依賴
npm install

# 2. 建立 .env 檔案，內容為：
ANTHROPIC_API_KEY=你的API金鑰

# 3. 啟動 server
node server.js

# 4. 打開 index.html（直接雙擊，或拖進瀏覽器）
```

測試路徑：
1. 畫面 1 可以自己輸入任務與背景，或點選下方三個範例任務（行銷提案／信件改寫／客戶退款）快速帶入文字
2. 按「開始預檢」，等待 AI 分析
3. 如果有值得詢問的不確定性，會跳出「關鍵一問」，用自由文字回答；如果沒有，會直接顯示可以建立工作契約
4. 看到工作契約（工作任務／已確認事項／人工澄清，皆附來源）
5. 按「開始執行」，AI 依契約產生成果，接著自動進行驗證，顯示逐項比對結果

離線備援：如果 API 額度或連線出狀況，可以打開 `index-standalone.html`，這是完整內嵌、不需要 server、使用固定 Mock 資料展示完整流程的版本，用於現場展示備援。

## 9. AI API 使用方式與安全性

- 前端 `ai-service.js` 呼叫我們自己的 server（`server.js`）上的三個 endpoint：`/api/analyze-task`、`/api/execute-task`、`/api/verify-result`
- `server.js` 再呼叫 Anthropic API
- API Key 全程只存在於 server 端的環境變數（`.env`），不會出現在任何前端程式碼、瀏覽器 devtools，也不會被提交到版控（`.env` 已加入 `.gitignore`）
- 模型的輸出被視為不可信任的語意資料：server 端會先嘗試解析 JSON（含去除模型可能誤加的 markdown 包裝），解析失敗會回傳明確錯誤而不是讓 server 崩潰

## 10. 已知限制

- 多輪澄清目前是「單次分析、逐題詢問」，不是「每題都重新完整分析」：見第6節說明，完整 re-evaluation 尚未實作
- **Verify 的能力邊界**：目前 Verify 檢查的是執行成果是否符合 Execution Contract 中明確列出的要求，屬於 contract-compliance verification，而不是對事實正確性、預測準確度或專業品質的形式化驗證。對預測、推薦、策略與創意判斷等沒有唯一正確答案的任務，只能確認成果是否遵守契約條件。此外，若模型在執行時加入契約之外的額外事實或推論，目前 verifier 也未必能完整偵測這類 unsupported additions（非正式壓力測試中，用一個體育賽事預測任務發現這個邊界，該案例不計入正式 evaluation）。
- 「處理既有內容」類任務依賴工作契約帶有完整原文：如果背景資訊只是「文章已提供」這類描述、沒有真正附上原文，AI 在執行階段會誠實回報缺少素材，而不是編造內容——這是我們認為正確的行為，但代表這類任務的品質直接取決於使用者提供的背景資訊夠不夠完整
- Execute 階段不做真正的外部工具整合：不會真的寄信、退款、寫入 CRM，只產生「應交付的工作成果」文字內容
- Evaluation 樣本數小：目前只做了 6 個開發期案例＋2 個額外新任務驗證，尚未進行大規模、完全獨立於開發過程之外的 unseen evaluation
- 目前只支援單一任務、單次 session 的分析，不支援跨對話記憶
