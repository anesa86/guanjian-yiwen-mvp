## 4. 系統流程
```
使用者輸入任務＋背景資訊
  → AI 抽取已知資訊
  → AI 找出缺漏與衝突（並判斷每項會影響哪些面向）
  → 用固定規則計算每個不確定事項的影響分數
  → 只挑出最高分且超過門檻的一項，作為關鍵問題
  → 使用者回答（或若都低於門檻，直接跳過）
  → 建立工作契約
  → AI 執行任務
  → AI 依工作契約驗證成果
  → 顯示成果與檢查結果
```

## 5. 技術架構
- 純前端（HTML / CSS / JS，無框架、無建置工具）
- `ai-service.js`：AI 邏輯的唯一入口，UI 完全不直接碰 AI 或 API
- 目前為 mock 階段，尚未串接任何真實 API

檔案結構：
```
index.html      四個畫面的 HTML 結構
style.css       樣式
app.js          畫面邏輯（切換畫面、綁定按鈕、渲染資料）
ai-service.js   AI 核心邏輯入口（analyzeTask / buildExecutionContract / executeTask / verifyResult）
mock-data.js    mock 資料與測試案例
```

## 6. 關鍵問題選擇機制
模型（未來）只需要判斷一個不確定事項「會影響哪些面向」，例如 `["strategy", "budget"]`。
分數由我們自己定義的固定規則計算，不是模型決定：

| 面向 | 分數 |
|---|---|
| 核心目標 | +5 |
| 對外／不可逆行動 | +5 |
| 主要內容／策略 | +4 |
| 預算／資源 | +4 |
| 使用者／受眾 | +3 |
| Deadline | +3 |
| 格式／表面呈現 | +1 |

只有「分數最高，且超過門檻」的不確定事項才會拿來詢問使用者；
若所有不確定事項都低於門檻，直接執行，不打斷使用者。

> 目前 MVP 展示的是「一輪只問一題」的情境。正式產品的邏輯是：
> 每一輪選出資訊價值最高、最可能改變執行結果的一題；
> 使用者回答後，若仍有其他高影響的不確定事項，理論上可以再進下一輪。

## 8. 執行方式
本機測試（不需要安裝任何套件）：

**如果只是要快速展示 / 在編輯器內建預覽測試（推薦）：**
直接打開 `index-standalone.html`。這個檔案把 CSS 和三支 JS 全部內嵌在同一個檔案裡，
不需要讀取任何外部檔案，不管是雙擊打開、拖進瀏覽器、或用編輯器內建的 HTML 預覽功能，
都不會因為「預覽工具沒有載入同資料夾的其他檔案」而按鈕沒反應。

**如果要照專案原本的檔案結構開發（`index.html` + 三支獨立 JS）：**
部分編輯器內建的 HTML 預覽面板，只會讀取你開啟的那一個檔案，不會一併讀取同資料夾裡
用 `<script src="...">` 引用的其他檔案，這種情況下 `index.html` 會打不開按鈕。
請改用瀏覽器直接開啟，或架一個簡單的本地伺服器：
```bash
# 在這個資料夾內執行
python3 -m http.server 8000
# 然後打開 http://localhost:8000
```

無論用哪個版本，測試路徑都一樣：
1. 畫面 1 的兩個欄位已經預填案例 C 的內容（不是 placeholder，是真的值），可以直接按「開始預檢」
2. 應該看到「關鍵一問」跳出來問 influencer 那題
3. 隨便輸入回答按「確認回答」
4. 看到工作契約，按「開始執行」
5. 看到「5 / 5 條件符合」

## 10. 已知限制
- 六個測試案例（A–F）目前都是 mock 資料，尚未真的由模型分析輸入內容；
  畫面 1 的案例按鈕只是切換要套用哪組 mock 資料，不是真的解析你打的文字
- 尚未接上任何真實 AI API
- 尚未實作多輪追問（目前每個案例只展示一輪）
- 契約 / 執行結果 / 驗證結果都是針對每個案例事先寫好的固定文字，
  不會因為你輸入的文字內容不同而改變（這正是等真 API 接上後要解決的事）
- Live AI 分析中，`field` 欄位的語意界定有時偏鬆散（例如把「等等寄給代理商」標成 deadline，
  但更接近交付對象/急迫性而非明確時間點），已知但尚未調整 prompt，待多測幾個案例後再一併處理
